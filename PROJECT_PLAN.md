# Fantasy Helper — NBA 9-cat H2H App Plan

## Context
Greenfield project (`/Users/dennis/Documents/projects/fantasy-helper` is empty). Two goals:
1. **Resume value**: a deployed, well-engineered full-stack app with a data core and an LLM agent on top. This reads well for backend, data, and AI roles.
2. **Win the league**: a 10-team, 9-category head-to-head ESPN league (public, single league, just me). Help with waivers, trades, matchup scouting, and league/punt analysis.

Decisions made: Python (FastAPI) + React (Next.js), Postgres, AWS, OpenAI tool-calling agent, ESPN data (nba_api optional), 1–2 month timeline.

Verified on day 1 (2026-10-20): league "Bicoastal Ballaz", ID 1396633554, season 2027, my team ID 4. Categories are the standard ESPN 9 (FG%, FT%, 3PM, REB, AST, STL, BLK, TO reversed, PTS), read from league settings. 19 regular-season weeks, then a 4-team playoff with two 2-week rounds.

### Findings that changed the plan
- **The schedule comes from ESPN.** Player data includes the full NBA schedule by scoring period (day), so games-remaining needs no second source. `nba_api` is now optional (only for game logs, if ever needed), which also removes the stats.nba.com-blocks-AWS risk.
- **Matchup weeks are irregular, and the API doesn't expose them.** Week 1 is 6 days and week 18 is 14 days (All-Star break). The calendar is a checked-in data file, validated on every ingest.
- **Local dev uses SQLite** (Docker isn't installed yet). The schema is portable; `docker-compose.yml` is ready for Postgres.
- **The project lives in iCloud-synced ~/Documents**, which hides the venv's `.pth` files and breaks imports. Tests and Alembic are configured with `src` on the path; moving the project out of iCloud is the real fix.
- **Live matchup predictor (added 2026-10-23).** Facts checked against the live API: scoring is `H2H_MOST_CATEGORIES` with no tiebreak (matchups can tie); 10 starting slots (PG, SG, SF, PF, C, G, F, UT×3) + 3 BE + 1 IR, locked per game, so benched games don't count; `mMatchup` scores include FGM/FGA/FTM/FTA, so live percentages combine with projected makes/attempts; past days' box scores come from `mRoster`/`kona_player_info` with `scoringPeriodId`; ESPN has no per-day projections, so we build them.
- **Live during games (changed 2026-10-27).** ESPN's matchup totals don't move during the day: on Oct 26 they were still 0 for every team after all of the day's games were final. They only count a day once it's processed. So "now" totals are summed from our own box scores: started games (not BE/IR) on completed days, plus today's lines so far. Today's lines come in the same `mRoster?scoringPeriodId=<today>` response we already fetch for set lineups. Re-fetched days 1-6 matched ESPN's week-1 totals in all 9 categories for all 10 teams; the stored copy was off by 1 STL for two teams (a later stat correction), so every ingest now re-fetches the current week's completed days. Game states (pre / live with the clock / final) come from ESPN's public NBA scoreboard; a game that has tipped is locked into the set slot and only the rest of it is projected. Each ingest warns if ESPN's totals match neither our completed days nor completed plus today. **Still to verify during a live game:** that `mRoster` lines update mid-game (probed only after games ended); the fallback is the NBA game summary box score.
- **Opponent stats come from ESPN's public, undocumented site API** (`statistics/byteam?category=opponent`), which can change without notice. If the fetch fails, the last stored set is kept and predictions fall back to no adjustment. Its team codes differ from the fantasy API's for 8 teams (mapped in `espn/parse.py`).

## Architecture
```
EventBridge (cron) → ingest job (ECS task) → Postgres (RDS)
                                               ↑
Next.js frontend ←→ FastAPI (App Runner/ECS) ──┤
                       └─ /agent → OpenAI tool-calling loop → calls the same analytics services
```
- **Ingestion** (`backend/src/fantasy_helper/ingest/`): `espn-api` provides league settings (incl. lineup slots and scoring type), rosters, free agents, stat windows, the NBA schedule and matchups (category totals plus makes/attempts). Replaces season tables atomically. Also keeps history that is never wiped: daily box scores (`player_game_stats`, missing days backfilled) and one prediction row per matchup per run (`matchup_predictions`, append-only). Opponent stats (`nba_team_opponent_stats`) come from ESPN's public site API. Runs on demand (`fh-ingest` or the UI's Refresh), during games too: today's lines and NBA game states (`live_game_stats`, `live_games`) make the totals live. ✅ built
- **Analytics core** (`backend/src/fantasy_helper/analytics/`): pure, unit-tested functions. This is the heart of the project:
  - `zscores.py`: per-cat z-scores over a configurable window (season / L14 / L7). FG% and FT% are **volume-weighted impact** (makes − league% × attempts). TO is negated.
  - `team_profile.py`: team per-cat totals, ranks, inferred punt cats.
  - `matchup.py` ✅: live weekly prediction = actual totals so far + Monte Carlo of the days left. Per player-game: blended rate (`rates.py`) × opponent factor (`opponent.py`), a chance of playing from injury status, and the daily 10-starter cap (`lineup.py`, priority by z-score). Variance is Poisson until box-score history allows a fitted dispersion (`variance.py`). Output: P(win/tie/loss), P(win) per cat, expected and most likely category score, projected finals. Run by the ingest and by `fh-predict`.
  - `waivers.py` ✅: rank free agents by what they do for *my* team, never by generic rank. Two rankings:
    - **Stream (this week):** re-run `matchup.py` against my actual opponent with the free agent swapped in for one of my players, starting from the first day he could play. Rank by Δ P(win matchup), the goal in a most-categories league, with Δ expected categories won as the tiebreak. Show the drop, the extra *started* games he adds after the lineup cap, and the per-category Δ P(win).
    - **Hold (rest of season):** Δ expected categories won per week against a league-average opponent, using blended rates and the remaining NBA schedule. Built as an expected-value calculation (daily lineup cap, everyone healthy) with a normal approximation per category, not a simulation, so it stays cheap over ~18 weeks.
    - **Category targeting comes from the opponent matchup.** Each category is labeled from its P(win): **locked** (> 90%), **swing** (10–90%) or **lost** (< 10%). Because the stream ranking measures win odds against this opponent, help in a swing category ranks high, help in a locked or lost category ranks low, and hurting a lost category costs nothing. A high-TO streamer is fine if TO is already lost, so weekly punting falls out automatically. The UI shows this board and which categories each candidate flips.
  - `trades.py` ✅: evaluate a trade for both sides with Hold's measure: Δ expected categories won per week against a league-average team over the weeks after this one (everyone healthy), plus Δ P(win a week) from the per-category odds treated as independent. The league average is recomputed with both rosters after the deal. Rosters stay legal: a side over the limit drops its lowest-priority players outside the deal, and a side that sends more than it gets picks up its best free agents for the open spots. The finder searches every 1-for-1 and 2-for-1 deal, both ways, with all 9 other teams (~18,800 for my team), screens them with a first-order estimate, and lists deals where both sides gain at least 0.05 categories a week (see Milestone 4).
  - `power.py` ✅: power rankings by rest-of-season strength, the expected share of weekly matchups a team would win playing every other team in every remaining week, next to the all-play record from completed weeks.
- **API** (`backend/src/fantasy_helper/api/`): REST endpoints wrapping each analytics function. Built so far ✅: league, this week's matchups, matchup detail with odds history, a team's week by player and day (`/lineup`, live today), a team's roster, category profile and moves (`/team`), every team's category profile (`/profiles`), power rankings (`/power`), waivers, a trade scored for both sides (`/trade`), the trade finder (`/trades`), and `POST /refresh` (runs the ingest). Results are cached in memory per snapshot.
- **Agent** (`backend/src/fantasy_helper/agent/`): OpenAI function calling. Tools = `get_my_team`, `get_matchup_projection`, `rank_waivers`, `evaluate_trade`, `find_trades`, `get_team_profile`, `player_lookup`. The LLM only explains and orchestrates; all numbers come from deterministic tools. Add a small **eval suite** (`agent/evals/`) of questions with expected tool calls and answer checks. This is a strong resume bullet.
- **Frontend** (`frontend/`, Next.js + TanStack Query + a chart lib): pages for Dashboard, Matchup, Waivers, Trade Lab, League Heatmap, Chat. Matchup, Team, League (heatmap + power rankings), Waivers and Trades ✅ (charts are hand-drawn SVG so far).

## Milestones (~8 weeks)
1. **Wk 1 – Data foundation** ✅: uv project, SQLAlchemy + Alembic, ESPN ingest, schema (leagues, teams, players, roster_entries, player_stat_lines, pro_games, matchups, ingest_runs), matchup calendar, 13 tests.
2. **Wk 2 – Analytics core** ✅: z-scores, team profiles, tests with pytest and fixture data.
3. **Wk 3 – Matchup + Waivers (MVP)**
   - **3a – Live matchup predictor** ✅: daily H2H win odds and expected category score. Required ingest additions (makes/attempts, lineup slots, box-score history, opponent stats) and new analytics (blended rates, lineup cap, opponent factors, dispersion fit).
   - **3b – Waivers + API + basic UI** ✅: the Stream and Hold rankings and the category board (see `waivers.py` above); REST endpoints; a first UI with Matchup and Waivers pages. *Usable for the season from here.*
     - **Still to verify** (needs the league settings page): what the league's add limit means. `mSettings` shows `matchupAcquisitionLimit: 0.43` and `matchupLimitPerScoringPeriod: true`, which is unclear. One guess: 3 adds per 7 days (3/7 ≈ 0.43), prorated for long weeks. Once confirmed, show adds remaining. Also confirm when a pickup can first play. The rankings assume the next day, with a "pickups can play today" switch, and the UI says neither is verified.
     - **Common random numbers** ✅: the baseline and every swap must reuse the same random draws for the players they share. Otherwise a 1–2 point Δ P(win) is simulation noise. Done in `matchup.py`: each player's chance of playing on a day is seeded per (side, player, day), and team totals are inverse-CDF draws from uniforms seeded per (side, stat) (`analytics/discrete.py`), so a swap shifts each draw a little instead of redrawing it. The waiver baseline uses the same seed as the Matchup page, so the two agree.
     - **Keep it fast** ✅: 200 free agents × 13 possible drops is too many full simulations. Free agents are screened to 25 by games he'd start this week × z-score value in swing categories (hold: remaining games × z-score value weighted toward my near-even categories), and drops are my 3 lowest-priority players. A few seconds per team, cached per snapshot.
     - **Assumptions stated in the UI** ✅: the opponent's roster stays fixed (they may stream too), and the ranking is for one move. Also: the dropped player keeps his games before the pickup can play, and the free-agent pool may include players still on waivers.
   - **3c – Live scoring + head-to-head Matchup + Team page** ✅: live totals and locked games on Refresh (see Findings), a Matchup page picked by matchup with both teams side by side and a day-by-day lineup view, and a Team page (roster averages, category specialists, punts, recent moves). `team_profile.py` now feeds the Team page. Trades are read from roster acquisitions, since ESPN's transactions view lists trades without their players unless signed in.
   - **Later, not in 3b:** multi-move streaming plans (a chain of add/drops through the week within the add limit), once single-swap rankings are proven against the backtest.
4. **Wk 4 – Trades + League view** ✅: trade evaluator/finder, 10-team category heatmap, punt detection, power rankings.
   - **Scope agreed (2026-10-28):** trades are scored with Hold's rest-of-season measure for both sides (not this week's Monte Carlo, since when ESPN processes a trade in this league isn't verified); the finder covers 1-for-1 and 2-for-1 deals; the League view is its own page; power rankings rank by rest-of-season all-play strength, since one completed week says little.
   - **Trades page:** the finder's deals (best for me first, each target with its best package, the roster moves each side makes, each player's z-score value) and an evaluator that takes up to 3 players a side, with the change per category for both teams. Players who are out, suspended or on IR are left out of the search; the evaluator takes them with a warning.
   - **League page:** power rankings (strength, categories per week against the field, all-play so far, punts) and a 10 × 9 heatmap of per-game team values shaded by league z, ranked, with punts (z < −1.5 from `team_profile.py`) outlined, over any stat window.
   - **The finder's screen** (findings on real data, Oct 2026): a first-order estimate (each player's expected weekly stats times the slope of the team's P(win) per category) correlates about 0.95 with the full score on a sample of deals, but on average overrates 2-for-1s by about 0.1-0.15 categories a week because it ignores the lineup cap. Ranking the screen by my gain alone mostly picked deals that failed the partner's minimum: 21 listable deals, nearly all with the weakest team, or 7 when each partner was screened separately. Screening each partner and each deal shape separately, by the smaller side's estimate, finds ~125 targets from ~300 full evaluations in about 2.5 s.
   - **Known limit:** the measure saturates. A team far behind in a category gains almost nothing from help there, so the finder can propose a star for role players to a team that punts the star's categories (e.g. Shai Gilgeous-Alexander to me from a team punting 3PM, AST and STL), and the model calls it a gain for them. The UI shows each player's z-score value so these stand out; a real manager would likely refuse. A value or acceptance check is a possible next step.
5. **Wk 5 – Agent**: OpenAI tool loop, streaming chat UI, evals.
6. **Wk 6 – AWS deploy**: Terraform (RDS, ECS/App Runner, EventBridge, Secrets Manager for the OpenAI key), GitHub Actions CI/CD, frontend on Amplify/Vercel.
7. **Wk 7–8 – Polish + resume extras**: backtest the stored `matchup_predictions` against final weekly results (Brier score / calibration; also tunes the blend constant, opponent shrinkage and day-to-day P(play)), observability (structured logs, agent token/cost tracking), README with architecture diagram, short demo video.
